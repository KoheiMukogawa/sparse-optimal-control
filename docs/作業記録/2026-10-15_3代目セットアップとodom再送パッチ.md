## 2. 【重要】3代目では odom が永久に出ない — 根本原因と対策

### 症状

`nav_base` の3ノードは生存しているのに `/odom` が1サンプルも出ない（`/tf` も無）。
再起動しても**毎回再現**する。

### 切り分け（systematic-debugging）

| 観測 | 意味 |
|---|---|
| `ros2 service call /wrc201_i2c {addr:96,cmd:r}` が即答（`read_data=0`） | サーバは正常 |
| `odom_manager` は CPU +20/300 jiffies・`wchan: futex_wait_queue_me` | ビジーループではなく待ち |
| Ctrl-C 時の traceback が `odometry.py:119 rclpy.spin_once` | そこで待ったまま死んだ |
| 最小再現スクリプトは 0.01s で応答（`create_rate(30)` と タイムアウト無し `spin_once` を
  同じにしても 0.084s で応答） | **コードパターンは無実。起動直後だけ失われる** |

### 根本原因

**`odometry.py` は起動直後に2件のサービス要求を投げ、応答を1回でも取りこぼすと
再送しない。** `getEncVal()` の再呼び出しが publish 成功の内側にしかないため、
DDSのディスカバリ完成前に投げた要求の応答が落ちると**自力では絶対に復帰できない**。

### 対策（RPi側 `odometry.py` にパッチ・要 `colcon build`）

```diff
     odom_manager.getEncVal()
+    last_req = time.time()
 
     while rclpy.ok():
-        rclpy.spin_once(odom_manager)
+        rclpy.spin_once(odom_manager, timeout_sec=0.1)
         get_val = None
         if odom_manager.enc_a.done() and odom_manager.enc_b.done():
             get_val_a = odom_manager.enc_a.result().read_data
             get_val_b = odom_manager.enc_b.result().read_data
             get_val = calSpeed([get_val_a, get_val_b])
 
         if get_val is None:
+            # 応答を1回でも取りこぼすと再送が無いため永久に待ち続ける。
+            # 起動直後のDDSディスカバリ競合で実際に発生した（2026-10-15）。
+            if time.time() - last_req > 1.0:
+                odom_manager.get_logger().warn(
+                    'i2c応答が1秒来ないので要求を再送する')
+                odom_manager.getEncVal()
+                last_req = time.time()
             continue
@@ publish 後
             odom_manager.getEncVal()
+            last_req = time.time()
```

**検証**: `/odom` が 31.46 Hz で流れた（7/15実機bagの基準 **29.94 Hz**・中央間隔32.7ms と一致）。
`odom_manager.log` に再送の警告が**毎回1回**出てから復帰する ＝ この機体では取りこぼしが
決定的に起きており、**このパッチ無しに3代目は動かない**。

**失敗した中間版の記録**: 最初は再送に加えて待機中に `time.sleep(0.025)` を入れたが、
**odom が 6.2Hz まで落ちた**（1周期160ms）。odomの報告遅れはむだ時間135msの構成要素
なので致命的。`spin_once(timeout_sec=0.1)` がブロックしてくれるので sleep は不要。

## 3. ROVER_D の再較正（3代目・別車体）

6/12 と同一条件（その場旋回360°・ω=0.4）で実施。**ω を揃えないと滑り量が変わるため比較不能。**

| | 旧車体（6/12・研究室の床） | 新車体（10/15・自宅の紙面） |
|---|---|---|
| 360°指示に対する実測 | 320〜330° | **357〜358°（−2〜−3°）** |
| 実/odom比 | 0.89〜0.92 | **0.993** |
| 残留滑り | 8〜11% | **0.7%** |

**その場旋回の滑りが一桁小さい。** 個体差というよりタイヤと接地面（自宅の床＋紙）の
組み合わせで横擦りが起きていないためと見られる。追従精度には良い方向。

補正値: `ROVER_D_new = 0.1514 × 360/357.5 = 0.1525`
→ `odometry.py` と `pos_controller.py` の両方を `0.1525/2.0` に変更し `colcon build` 済み。
**ただし検証の旋回は未実施（次回の最初の作業）。**

判定基準: 実測 **360±1°** なら採用 ／ **−2°以上足りなければ補正不足** ／
**+2°以上行き過ぎなら過補正で 0.1514 に戻す**。

バックアップ: `odometry.py.bak_retry`（再送パッチ前）・`*.bak_d1514`（ROVER_D変更前）・
`*.orig`（ベンダ原版）。
