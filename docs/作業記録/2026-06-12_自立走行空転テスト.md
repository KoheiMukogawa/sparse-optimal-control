# 自立走行テスト 作業報告書（空転＋床実走行）

**作業日: 2026年6月12日**
**ブランチ: exp/autonomous-drive**

---

## 概要

公式サンプル `vstoneofficial/lightrover_ros2` を土台に、Kanayama制御則による
経路追従ノードを実装し、実機LiteRover（ジャッキアップ・車輪空転状態）で
直線2mとL字経路の自立走行を確認した。SLAM・AMCL・DDS（ラップトップ↔RPi通信）は
使わず、**/odomのみ・RPi完結構成**で自立走行の最小構成を成立させた。

## 1. 公式サンプルの調査結果

`vstoneofficial/lightrover_ros2`（Humble対応）を調査し、以下が判明:

| 項目 | 内容 |
|------|------|
| 速度指令トピック | **`rover_twist`**（`/cmd_vel` ではない。Nav2用launchでremapしている） |
| オドメトリ | `odom_manager` が `/odom`（約30Hz）とTF（odom→base_footprint）を配信 |
| 車輪制御 | `pos_controller` が rover_twist を受け、I2C経由で車輪レベルのP制御 |
| 速度レンジ | ゲームパッド基準で並進 0.1 m/s、旋回 2.0 rad/s |
| 自立走行用launch | `nav_base.launch.py`（i2c + odom + pos_controller + LiDAR、gamepadなし） |

**結論: モータ制御・オドメトリはサンプル流用で済み、自作は経路追従ノード1個のみ。**

注意: `pos_joycon.launch.py` はgamepadノードが rover_twist を配信するため、
自立走行ノードと指令が競合する。自立走行時は `nav_base.launch.py` を使うこと。

## 2. 実装

### 構成

```
rover/
  follower_core.py      # 経路射影・Kanayama誤差・制御則（ROS非依存）
  path_follower.py      # ROS2ノード: /odom購読 → rover_twist配信
  test_follower_sim.py  # 運動学モデルでのクローズドループ検証
configs/
  path_straight_2m.yaml # 直線2m
  path_L_turn.yaml      # 直線1.5m + 左90度 + 直線1.5m
```

純粋ロジック（follower_core）とROSノードを分離したのは、
後でKanayama制御則をL1スパースMPCに差し替える際、
同じ経路射影・誤差計算を流用するため。

### 制御則（Kanayama）

参照姿勢は経路（折れ線）への射影点から lookahead = 0.15m 先に置く。
誤差（ロボット座標系）(x_e, y_e, θ_e) に対し:

- v = v_r cosθ_e + K_x x_e
- ω = ω_r + v_r (K_y y_e + K_θ sinθ_e)、直線経路なので ω_r = 0

ゲイン: K_x=0.5, K_y=5.0, K_θ=3.0（シミュレーションで決定、実走行で要再調整）
制限: v_r=0.1 m/s, |v|≤0.15 m/s, |ω|≤2.0 rad/s（ゲームパッドのレンジに準拠）

### 安全機構

- odomが0.5秒途絶したら停止指令を配信
- ノード終了時（Ctrl+C含む）に必ず停止指令を配信

## 3. シミュレーション検証で発見・修正したバグ

実機投入前に運動学モデルでのクローズドループ検証を行い、2件のバグを修正:

1. **ゴール超過点での停滞**: ゴール手前で減速しないと、v_r cosθ_e と K_x x_e が
   釣り合う「ゴールの v_r/K_x = 20cm 先」が安定平衡点になり、到達判定圏
   （5cm）に入らないまま停止する。
   → ゴールから0.3m以内で基準速度を距離比例で減速する `goal_scaled_vr` を追加。
2. **横偏差残留時の未到達**: コーナーで横にふくらんだままゴール脇を通過すると、
   円形の到達判定（半径5cm）に入らない。
   → 最終セグメントに垂直な「ゴール線」の通過判定 `goal_crossed` を追加。
   経路追従実験では走り切りが重要で、最終姿勢のズレはRMSE側で評価するため
   この判定が適切。

修正後のシミュレーション結果（20Hz、初期ズレ各種）:

| ケース | 結果 | 所要時間 | 横偏差RMSE |
|--------|------|---------|-----------|
| 直線2m（経路上スタート） | 到達 | 13.7s | 0.0cm |
| 直線2m（横20cm・30度ズレ） | 到達 | 14.2s | 16.9cm |
| 直線2m（横-30cm・-45度ズレ） | 到達 | 14.4s | 23.0cm |
| L字（経路上スタート） | 到達 | 22.8s | 11.6cm |
| L字（横15cmズレ） | 到達 | 22.8s | 12.6cm |

## 4. 実機環境の修正（transforms3d非互換）

`nav_base.launch.py` 起動時に odom_manager が即死する問題が発生。

- 原因: apt版 transforms3d 0.3.1（`/usr/lib/python3/dist-packages`）が `np.float` を
  使用しており、ユーザーローカルの新しい numpy 1.26.4 と非互換
  （`AttributeError: module 'numpy' has no attribute 'float'`）
- 対処: `pip install --user --upgrade transforms3d` → 0.4.2 がユーザーローカルに
  入り、apt版をシャドウして解決（sudo不要・apt環境は不変更）

## 7. 床での実走行テスト（同日午後・モバイルバッテリー給電）

RPiをシャットダウン後モバイルバッテリーに切替（モータはVS-WRC201側の
単3ニッケル水素×4で別系統のため差し替えはRPiのUSB-Cのみ）。
直線2m経路を3本走行し、rosbagで /odom, /rover_twist, /path_error を記録した。

### 結果

| Run | 所要時間 | odom走行距離 | odom横ズレ | 備考 |
|-----|---------|-------------|-----------|------|
| 1 | 13.8s | 1.958m | -1.1mm | 完走・自動停止 |
| 2 | 13.7s | 1.955m | 0.1mm | 完走・自動停止 |
| 3 | 13.7s | 1.958m | 2mm（経路座標換算） | 完走・自動停止。実測あり |

**Run 3の実測（メジャー）: 直進距離192〜193cm、軌道はまっすぐ。**

- odom 1.958m vs 実測 1.92〜1.93m → **odomは約1.5%過大**（車輪径・
  エンコーダ定数の系統誤差）。数mスケールの実験には十分、長距離では補正要
- 横方向は実測・odomとも良好（左右輪バランス良）
- rosbagは `results/2026-06-12_floor_runs/` に回収済み

### L字経路（90°旋回入り）の床走行

直線1.5m → 左90° → 直線1.5m。所要23.0秒（シミュレーション予測22.8秒）で
完走・自動停止。Run 4としてrosbag記録済み。

| 項目 | 計画/odom | 実測 | 評価 |
|------|----------|------|------|
| 旋回開始点 | 約1.35m（1.5m−lookahead 0.15m） | 1.33m過ぎから | 設計通り |
| 旋回半径 | — | 約40cm | 観察記録 |
| 旋回後の走行距離 | 1.50m | 1.52〜1.53m | 直線同様の約1.5%過大 |
| 旋回角度 | 90° | **約80°** | **約10°不足（odomの角度が約11%過大）** |

**最重要の発見: 角度オドメトリの系統誤差。** odom上は90°旋回を完了した
ことになっているが、実際は約80°しか回っておらず、旋回後の進行方向が
意図より右に10°ずれた。原因候補:

1. 旋回時の車輪スリップ（タイヤが床を横に擦る分、エンコーダが回転を過大計上）
2. odometryのトレッド定数 ROVER_D=0.143m が実効値とずれている
   （80/90から逆算すると実効トレッド ≈ 0.161m 相当）

直進1.5%に対し回転11%と誤差が一桁違うため、**odomのみ構成の限界は回転にある**。
対策候補（要検証）:
- その場旋回キャリブレーション（N回転コマンド vs 実回転角で補正係数を同定）
- 床材依存の可能性があるため、実験場所ごとに補正係数を取る
- 本実験は旋回回数の少ない経路で設計する／最終的にはSLAM・AMCLで姿勢補正

### 発見したバグと対策: odomオフセットの引き継ぎ

3本目の準備でベースノードを再起動した際、odomが (0.53, -0.87) から始まり、
ロボットが「経路の右0.87mにいる」と誤認して**左に大きく逸れる**事象が発生
（即時手動停止）。

- 原因: サンプルの `odometry.py` は起動時に前回エンコーダ値を0と仮定するが、
  VS-WRC201基板の累積カウントは基板の電源が入っている限り保持されるため、
  ノード再起動時に過去の走行分が初回の1ステップとして一括積算される
- 対策: **path_follower起動時の自己位置・向きを経路原点とする方式に改修**
  （waypointsを起動時姿勢で座標変換）。これによりodomのゼロ点に依存しなくなり、
  ベースノード再起動の儀式も不要になった（置いた場所・向き＝スタート）

## 8. 回転オドメトリのキャリブレーション（同日夕方）

### 8.1 follower側yaw補正の失敗と教訓（run5）

L字の旋回角不足（実80°/odom90°）に対し、まずpath_followerにヨー角補正係数
（yaw_scale=0.889）を入れて走行（run5）。bag解析の結果:

- 指令プロファイルはrun4とほぼ同一 → **followerは位置項に支配されており、
  ヨー角だけの補正は実質無効**（位置はRPi側で未補正ヨーにより積算済みのため）
- 補正はodometryの積算定数そのものに入れる必要があると判断し、yaw_scaleは撤去
- なおrun5でユーザーは「右に曲がった」と観察したが、bagの指令・odomとも
  左旋回で一貫しており、後続の旋回テストでも左回り確認 → 観察時の混乱と推定

### 8.2 その場旋回テストによる滑りの定量化

spin_test.py（odom上で指定角回転して停止）を作成し、実回転角と比較:

| 条件 | odom指示 | 実測 | 実/odom比 |
|------|---------|------|----------|
| D=0.143（元）, ω=0.4 | 360° | 約340° | 0.944 |
| D=0.1514（補正後）, ω=0.4 | 360° | 320〜330° | 0.89〜0.92 |
| D=0.1514（補正後）, ω=0.2 | 360° | 約340° | 0.944 |

- **滑りは回転速度に依存**（補正でホイール速度が上がると滑りも増えて相殺）
- その場旋回は両輪逆転でタイヤ横擦りが最大になる最悪条件であり、
  低速でも5〜6%の滑りが残る → 定数補正だけでは消えない

### 8.3 トレッド定数補正とアーク旋回での検証（run6, run7）

- 補正: `odometry.py` と `pos_controller.py` の ROVER_D を
  0.143/2 → **0.1514/2**（=0.143×360/340）に変更し再ビルド
  （RPiの `~/ros2_ws/src/lightrover_ros2`。元ファイルは `.orig` で保存）
- L字走行で検証（run7・実測）:

| 項目 | run4（補正前） | run7（補正後） |
|------|--------------|--------------|
| 旋回角 | 約80° | **ほぼ90°** |
| 旋回開始位置 | 1.33m過ぎ | 1.33m過ぎ（設計1.35m） |
| 旋回後直進 | 1.52〜1.53m | 1.50m |

**結論: 実験で使う前進アーク旋回では、トレッド定数補正で旋回角がほぼ設計値
になった。** その場旋回の残留滑りは実験条件として使わないため許容し、記録のみ。
