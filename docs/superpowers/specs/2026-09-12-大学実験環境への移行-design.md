# 大学実験環境への移行（2代目LiteRover＋方眼紙走行面）設計（2026-09-12 承認済み）

## 背景・目的

- 初代 RPi4 が SoC/基板レベルで故障（2026-08-01 判定、8/31 にテスト0-b で独立に裏づけ）。
  **2代目の LiteRover が手元にあり**、これで実機タスクを再開する。
- 実験場所が自宅から**大学**へ移る。カメラ真値計測系（AprilTag 俯瞰・C270）は
  **俯瞰カメラの設置位置が確保できず、設置場所が毎回変わる**ため大学では使えない。
- 走行面を**方眼紙（大判紙に自分で墨出し）**に置き換え、真値計測を
  「カメラ自動」から「方眼直読＋ペン軌跡」へ設計しなおす。

## 前提の再確認（調査で判明した事実）

ここが今回の設計の土台なので明記する。

- **卒論の実機真値はもともと手計測である。**
  `chapter6.md:221` 表6.5「真値計測による終点誤差」は
  「外部計測による終点誤差（実機 n=3）」＝**メジャーの手実測**。
  カメラ真値が本文に出るのは 6.6節の妥当性検証（表6.6b：カメラ 92.8cm /
  手実測 94.5cm / 一致 2.5cm・1.6°）**だけ**で、しかも**手実測が基準側**。
  → 「カメラのほうが精度が高い」は成立しない。カメラを外しても第6章の論証は落ちない。
- **6.7節の「真値RMSE vs 計測RMSE」は sim（S4）の話**であり、
  実機の真値 RMSE 時系列は**元から持っていない**（7.6節の限界8）。
- **カメラを外して本当に失うのは `--auto` の無人化である。**
  `run_batch.py` の自動ループは「走行 → 真値stop → CSV → 自動原点復帰 → 次へ」で、
  `homing.py` はカメラ pose を状態量に Kanayama で原点へ戻す。
  ただし `run_batch.py` のカメラ依存は **`if args.auto:` の中だけに閉じており**、
  非auto の実機バッチ（`--backend real`）は**今日そのまま動く**。
  走行間の `input("次: …")` プロンプトも `exp_backends.py:314` に既にある。
- `homing.py:22` の `TOL_YAW = 2°`（理由コメント：開始向き残差は 1.4m 先で
  `sin θ × 140cm` 効く）。**手動リセットで 2° を再現できるか**が唯一の争点だった
  → 床にテープを貼ってよく半日占有できるため、基準線＋車体2点合わせで成立する。

## 決定事項（ブレインストーミング結果）

- **走行面**: 無地の大判紙に**自分で 10cm 格子を墨出し**（1.5m 角で足りるが 2m 角推奨）。
  方眼模造紙の継ぎ合わせは**継ぎ目で座標系がずれる**ため採らない。
- **真値計測**: 終点誤差は**方眼直読**、走行軌跡は**駆動軸中心に垂らしたペン**で紙に描く。
- **原点復帰**: 自動 homing を使わず、**紙面の基準線に車体2点を合わせる手動リセット**。
  加えて**毎走行の開始姿勢ズレ（x,y [mm] / θ [deg]）を記録する**。
- **既刊データとの接続**: **大学・2代目で一本化**。表6.5 相当（3者比較＋Kanayama）も
  大学で撮り直し、実機章の数値を全て新環境に揃える。
- **カメラ真値パイプライン**: 実験系からは外すが**卒論からは削らない**。
  4.5節は「構築し妥当性を検証した（表6.6b）が、大学の実験環境の制約で
  本バッチでは手実測を採用した」と書く。7章の限界に正直に載せる。

## コース寸法の妥当性

コースは `configs/path_L_turn_1m.yaml`：`(0,0) → (1,0) → (1,1)` の 1m L字。
実走行範囲はコーナー外側への系統誤差（4.9節、外部計測9走行すべてで発現）と
オーバーシュート込みで **x: −0.2〜1.3m / y: −0.3〜1.2m** 程度。
→ **1.5m 角で足り、2m 角なら余裕**。`homing.py` の安全柵 `MARGIN_M=0.30` とも整合。

## 走行面の作り方

無地の大判紙に以下を墨出しする。座標系の定義は**既刊と同一**
（原点=走行原点、x=第1直進方向、y=左）とし、**解析コード側は変更しない**。

| 描くもの | 内容 |
|---|---|
| 10cm 格子 | 全面。1m ごとに太線 |
| 原点の十字 | `(0,0)`。車体の駆動軸中心をここに合わせる |
| +x 方向の太線 | 第1直進方向 |
| コース線（薄線） | `(0,0)→(1,0)→(1,1)` |
| 開始姿勢の基準線 | 車体の前後2点を載せる線。2点間が長いほど θ 再現性が上がる |

四隅と辺の中点を養生テープで床に固定する（Phase 2+3 の全30走行と手動リセットの
往復で中央が動くため、四隅だけでは足りない）。

## 1走行あたりのプロトコル（3〜5分）

1. 車体を基準線に合わせて設置し、**開始姿勢のズレを方眼で読んで記録**（x,y [mm] / θ [deg]）
2. 走行（駆動軸中心のペンが軌跡を描く）
3. 終点で駆動軸中心を方眼で読む → x, y, θ（θ は車体2点読みから `atan`）
4. bag 回収 → Σ|u| ・ω符号反転・ゼロ率・求解時間・OSQP反復数
5. 軌跡を真上から1枚撮影（走行ごとにペン色を替える。色が尽きたら紙を張り替え）

## 取得データと卒論への接続

| データ | 手段 | 接続先 |
|---|---|---|
| 終点誤差 x, y, θ | 方眼直読（数mm / 1°以下） | 表6.5（**大学・2代目で一本化**） |
| **実機の真値 RMSE** | ペン軌跡の読み取り | **新規**。7.6節の限界8 を解消し、6.7節が sim 限定でなくなる |
| Σ\|u\| ・ゼロ率・符号反転・求解時間・反復数 | bag | 6.2〜6.4節（カメラ不要） |
| 開始姿勢のばらつき | 方眼直読 | 6.4節 rep1 外れ値（34.5cm）の原因特定 |

既刊のメジャー実測は `93cm / 97cm / 4°`（`chapter4.md:269`）。
方眼直読は x,y が数mm、θ が 1° 以下まで詰まるため、**手実測の精度が
カメラ真値（2.5cm / 1.6°）を明確に上回る**。

## R5（入力遅延の直接実測）— 手順の再設計

`outline.md:781` の当初手順は「ω ステップ指令 → **カメラ真値の角速度応答**との時間差」で、
カメラ前提だった。これは 5.6 / 7.6 / 8.1 の中心的主張（「約200ms」）を
推定値から実測値へ格上げする★★★タスクであり、代替手順が要る。

**予備計測1本で判定する**：

1. **第1候補: odom の ω 立ち上がりで測る。**
   odom は滑りで絶対値が歪むが、立ち上がり時刻は車輪エンコーダ由来なので取れる可能性がある。
   そもそも制御ループが実際に見ている遅延は「指令 → odom 反映」なので、
   **むしろこちらが測るべき量**かもしれない。
   ただし **odom パイプライン自体が持つ遅延と切り分けられるか**が未確認。
2. **第2候補: スマホ240fps 動画。** 指令送出と同時に LED を点けて時刻同期し、
   車輪の動き出しをコマで読む。

1 が使えるかを Phase 0 で判定し、駄目なら 2 に切り替える。

## 所要時間

純粋な走行時間は **45〜60本 × 約4分 = 3〜4時間**。残りは設置・較正・測定・トラブル対応。

| 日 | 内容 |
|---|---|
| D1 準備（フル1日） | 紙の墨出し 1〜2h（**自宅で先行可**）／2代目セットアップ 半日／紙面で `spin_test` 再較正 1〜2h／写真 30分 |
| D2 本命（フル1日） | スモーク2本 1h → load000 12本 2h → **R5 遅延実測 2〜3h** |

予備日は削らない。解析・作図・本文反映がさらに **2〜3日** で、
合計 **実験4日＋解析3日 ≒ 1週間強**。

### ペン軌跡の読み取りコスト（見積もりで判明した問題）

手で方眼を読むと1枚 10〜15分。60本なら **10〜15時間**で、実験日とは別にこれが乗る。
対策は両方採る：

1. **写真からの軌跡抽出スクリプトを作る**（半日）。1枚 1〜2分に落ちる
2. **真値RMSE の対象は Phase 2 の12本に限定**し、Phase 3 以降は終点誤差のみにする
